# 自动发版流水线：三条规则、一个事件

> 这套东西跑在哪由**中台规则**决定，不写在项目里。这份文档是给人看的全局图：
> 一个事件进去，谁在哪一步接手、产出什么、在哪能挡住。
> 规则的权威配置在 `~/Projects/nas-ops/hub/rules.json`；三份步骤手册在 `.dsh/skills/`。

## 一句话

你发**一个** `context-domains.task` 事件，然后什么都不用管：

```
分析 → 开发自测 → 收尾  →【检查：五问】→ 上线
      cdx-task             cdx-check        cdx-release
```

开发自己做完前半程，交棒给检查；检查不过退回开发或分析，过了交给上线。

## 事件对照表

| 事件类型 | 谁发 | 谁接 | 含义 |
|---|---|---|---|
| `context-domains.task` | 你（或别的规则） | 开发 | 一件新活 |
| `context-domains.build` | 检查 | 开发 | 退回：哪一问没过、证据是什么 |
| `context-domains.check` | 开发 | 检查 | 交棒：做了什么、verify 多少项、plan 在哪 |
| `context-domains.ready` | 检查 | 上线 | 通过：五问全过，可以发 |

## 五问在哪一行

在 `.dsh/skills/cdx-check/SKILL.md` 的表格里，第 12 行起。**开发这条规则里没有五问**——它只有四段。

| 问 | 核什么 | 不合格退回 |
|---|---|---|
| 1 | todo 真的全做完了？ | 开发 |
| 2 | 代码是对的？ | 开发 |
| 3 | 页面上真的对？ | 开发 |
| 4 | 用户目标达成了？ | 目标本身错了 → **分析**；只是没做到 → 开发 |
| 5 | 基线对不对？ | 偏差改变结论才退；不改变就带修正通过 |

第 4 问是唯一会一路退回**分析**的：发现「这个目标一开始就定错了」，改代码没用。

## 四次动手前的边界

**① 开发和检查都只有 30 分钟。**
19 条那种大改造跑不完（`settings-lag` 实测 36 分钟），会超时中断重试。真遇到靠 `later` 约下一轮 + `resume` 接会话，但**这两个机制至今零次实测**。

**② 检查也是 `access: edit`，能改代码。**
拦它的只有 skill 里那句「底线：不许改代码」。`access` 在这个环境不提供写保护：`read-only` 和 `workspace-write` 下 `bash` 与 `write` 工具实测都能写文件（只有写 `/etc` 被 Linux 用户权限挡住）。别拿 `access` 当安全边界。

**③ 退回最多约三次。**
每发一次事件 hops 加 1，超过 8 层只记录不派发：

```
task(0) → check(1) → build(2) → check(3) → build(4) → check(5) → build(6) → check(7) → ready(8)
```

第 4 次退回就撞上限。撞到说明需求没定清楚，回头改需求，别继续退。

**④ 上线是终点。** 它不发任何事件，发出去就结束了。发坏了不删 tag 重建（Release 会变 untagged draft、稳定别名静默 404），bump 到下一个版本再发一版。

## 已经验证到哪一步

| 机制 | 验证状态 |
|---|---|
| 开发 → 检查 → 上线 全链 | ✅ 2026-11-24 `mask-guard` 一次跑通（46 分钟，v0.4.5） |
| 开发自测合一条 | ✅ 两轮（19 条与 6 条 todo 各一次） |
| 检查独立核对 | ✅ 自己重跑 verify 与 e2e，还发现开发漏掉的会话级状态视野 |
| `build` 退回 | ❌ 从未触发 |
| `later` + `resume` 跨轮 | ❌ 从未触发（`timers` 表 0 条） |
| 单轮 30 分钟内做完大任务 | ❌ 19 条那种会超时 |

## 谁能挡住什么

| 想要的拦截 | 靠什么 | 可靠吗 |
|---|---|---|
| 五问有一问不过 | 检查发 `build` 退回 | 靠 agent 判断 |
| 测试污染真实数据 | `test/e2e/guard.mjs` 的 `guardDomains()` | 硬：抛错中止 |
| 发版前没过测试 | `release.yml` 的 `Verify` 步骤 | 硬：CI 红 |
| 版本号与 tag 不一致 | `release.yml` 的 `Resolve version` | 硬：CI 红 |
| 往别人的仓库写（市场 PR） | 规则 `askFirst` + skill 要求先 `ask` | 靠 agent 守 |
| 检查不许改代码 | skill 里一句话 | ✗ 软约束，沙箱不拦 |

结论：**真正硬的都在 CI 和测试里；规则层的拦截靠 agent 守纪律。** 所以 skill 写得具体比规则配得花哨更有用。
